Environment Variables & Docker — Explained

What is an environment variable?

Think of an environment variable as a setting your app reads when it starts up — like a configuration dial you can adjust without changing the code itself.

A simple analogy: imagine your app is a coffee machine. The code is the machine's internal workings, but environment variables are like the settings panel — you can dial in "make 2 cups" or "make 10 cups" without rewiring anything inside.

Why do you need them here?

Your app needs to connect to a database, and to do that it needs to know two things:

  • What's the database called? → DATABASE_NAME
  • Where is the database? → DATABASE_HOST

Right now, those values are hardcoded defaults in your app (book_store_test and probably localhost). But when you deploy with Docker, both of those answers change — so instead of editing the code every time, you pass in environment variables to override the defaults.

The three options

Option 1

Bake into Dockerfile

Values get built into the image. Use when the value never changes between environments.

✓ Your situation

Option 2

Pass at runtime

Use -e or --env-file when the value differs between dev, staging, and prod.

For later, when you scale up.

Option 3

Runtime — secrets

Passwords, API keys. Never bake these in — they're visible in the image history.

⚠ Security risk if ignored.

Why Option 1 is fine for you right now: since your Docker setup always uses the same database host and name, the values won't change between runs. So it's safe and simple to write them directly into the Dockerfile — no need for the extra complexity of Options 2 or 3 yet.

Setting env vars in a Dockerfile

You use the ENV instruction. It looks like this:

FROM python:3.11
ENV DATABASE_NAME=book_store
ENV DATABASE_HOST=db

When Docker builds your image, those values get baked in — every container you run from that image will automatically have those variables available.

How your app reads them

Your app code doesn't care how the variable was set — it just reads it by name. In Python it looks like this:

import os
db_name = os.environ.get("DATABASE_NAME", "book_store_test")

The second argument ("book_store_test") is the default — what the app falls back to if no environment variable is found. That's why your deployed app was using book_store_test before: no variable was set, so it used the fallback. By adding ENV DATABASE_NAME=book_store to your Dockerfile, you're overriding that default.

What "baked in" actually means

When you run docker build, Docker executes each line of your Dockerfile in sequence and commits the result as a layer. The ENV lines become part of the image itself — you can inspect them later with docker inspect <image-name>.

This is also why you shouldn't bake in secrets — anyone with access to the image can read them, even if you deleted the variable in a later layer.

Multiple variables at once

You can set several on one line, which is slightly cleaner:

ENV DATABASE_NAME=book_store \
    DATABASE_HOST=db

The practical upshot for your project

Your Dockerfile probably already has a FROM line, a COPY, and a RUN. You just need to add two ENV lines somewhere before the CMD at the end:

FROM python:3.11
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt

ENV DATABASE_NAME=book_store
ENV DATABASE_HOST=db

CMD ["python", "app.py"]

After rebuilding the image (docker build), any container you run from it will automatically connect to the right database — no extra flags needed.
